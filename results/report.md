# Подробный отчёт

Здесь собраны все цифры бенчмарка.

Главная метрика везде MRR@10. Она показывает, насколько высоко в выдаче стоит правильный chunk: 1.0 значит, что он всегда первый, 0.5 значит, что в среднем второй, 0 значит, что его нет в первой десятке.

Если не сказано иное, число усреднено по пяти языкам программирования, и каждый язык весит одинаково.

Языки: csharp, go, java, python, typescript. Обычных вопросов: 2000. Прогонов: 95, из них 86 с разными результатами. Остальные дали ответы один в один с другой сборкой той же модели.

Несколько слов, которые встречаются ниже.

| Термин | Что значит |
|---|---|
| RAG | схема, в которой языковая модель отвечает на вопрос по найденным chunks |
| Chunk | один класс, метод или функция; правильный ответ на вопрос задаётся chunk |
| Window | часть chunk, которую модель превращает в вектор; длинный chunk режется на windows по 1500 символов, и chunk получает оценку своего лучшего window |
| Late interaction | модели, которые хранят не один вектор на window, а вектор на каждый токен |
| IVF_HNSW_PQ | ANN-индекс в векторной базе: ищет быстрее точного перебора, но может что-то пропустить |
| Bootstrap | оценка разброса результата: набор вопросов много раз пересобирается случайным образом |
| Holm correction | нужна, когда сравнений много: без неё часть различий оказалась бы «значимой» случайно |

## 1. Общий рейтинг

Здесь все модели на 2000 обычных вопросах.

В квадратных скобках диапазон, в котором с вероятностью 95% лежит настоящее значение, если бы вопросов было намного больше.

| Колонка | Что значит |
|---|---|
| nDCG@10 | похожа на MRR@10, но учитывает и остальные правильные chunks ниже первого |
| R@10, R@30 | доля вопросов, где правильный chunk попал в первые 10 и 30 результатов |
| R@30 в контексте LLM | доля вопросов, где правильный chunk попал в те 30 chunks, которые RAG передаёт языковой модели, когда с одного файла берётся не больше 2–4 chunks |
| MRR@10 (1-е window) | та же метрика, если chunk оценивать по первому window, а не по лучшему; так я проверяю, что порядок моделей не зависит от этой детали |
| Δ к лидеру | на сколько модель хуже лидера (st:ai-sage/Giga-Embeddings-instruct-3B-0826); звёздочка значит, что отставание не случайно, без звёздочки модель от лидера статистически не отличается |

Модели с припиской вроде @w800 это та же модель на другой нарезке кода, про них раздел 7.

pplx-embed-context-v1-4b учитывает соседний код файла. С припиской @g2048 она получает windows одного файла подряд, группами до 2048 токенов, и вектор каждого window строится с учётом соседей. С припиской @g0 каждое window кодируется отдельно, без соседей. Разница между ними показывает, сколько даёт контекст файла.

У late:perplexity-ai/pplx-embed-v2-late-0.6b индекс на 5 проектов весит около 2 ГБ (float16, 128 чисел на каждый токен). Индекс с одним вектором из 1024 чисел (float32) на window весит около 0.1 ГБ, примерно в 21 раз меньше. Индекс лидера с вектором из 2048 чисел меньше примерно в 10 раз.

## 3. В чём именно модель лучше

Я разбил обычные вопросы на группы четырьмя способами и для каждой группы посчитал MRR@10.

| Разрез | Какие группы |
|---|---|
| Язык комментариев | есть ли в правильном chunk кода русские комментарии; если нет, модели приходится сопоставлять русский вопрос с чисто английским кодом |
| Тип вопроса | как работает код (behavior), что происходит при условии (condition), какие поля и параметры (data), где реализовано (location), зачем сделано именно так (rationale) |
| Размер chunk | short помещается в один window, medium режется на два–четыре windows, long на пять и больше |
| Близнец | есть ли в проекте почти такой же chunk, с которым модель может спутать правильный |

Каждую группу я считаю внутри языка и потом усредняю по языкам, где в ней хотя бы 20 вопросов. Сколько таких языков, написано в шапке колонки.

>
> Обратите внимание на multilingual-e5-large-instruct. На коде только с английскими комментариями у неё 0.10, а с русскими 0.65.
>
> Так же ведёт себя BM25, full-text search без нейросети (0.02 и 0.32). Модель находит код в основном по русским словам в комментариях и почти не связывает русский вопрос с английским кодом.

> Это не ошибка запуска. Префикс взят из карточки модели, а на windows по 800 символов, которые целиком помещаются в её контекст, результат тот же.

## 10. Стратегии поиска

Для четырёх моделей я сравнил разные способы поиска в настоящей векторной базе LanceDB. В каждой ячейке MRR@10 и через косую черту R@30 в контексте LLM.

| Стратегия | Как ищет |
|---|---|
| vector_exact | точный поиск по векторам |
| vector_ann | то же через ANN-индекс IVF_HNSW_PQ с nprobes 24 и refine_factor 8: лучших кандидатов индекс пересчитывает по полным векторам, поэтому результат совпадает с точным поиском |
| fts_only | только full-text search LanceDB (BM25), топ-40. Это другая реализация BM25, чем в общем рейтинге, поэтому на обычных вопросах 0.207, а не 0.225: в рейтинге свой токенизатор, который ещё делит идентификаторы вида parseHttpRequest на части |
| rrf | hybrid search: смешивает выдачу vector search и full-text search по местам в списках |
| routed | rrf, если в вопросе есть имя из кода, иначе вектор |
| routed_usage | rrf для вопросов «где используется» и «откуда вызывается», иначе вектор |
| hybrid_ann_bm25=w | hybrid search: смешивает оценки двух поисков, w это вес full-text search |
